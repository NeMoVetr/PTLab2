# Магазин предметов роскоши

Учебное приложение Django: каталог часов, сумок, украшений и аксессуаров,
оформление покупки одной единицы товара, учёт остатков в PostgreSQL.
Лицензия — [MIT](LICENSE): допускает использование, изменение и распространение
кода с сохранением уведомления об авторских правах и текста лицензии.

## Запуск

Требуются Python 3.14+, uv и PostgreSQL. Создайте базу `prog_tech_lab_2`,
скопируйте `.env.example` в `.env`, задайте свой секретный ключ и пароль БД.
Переменные окружения процесса имеют приоритет над `.env`.

```shell
uv sync --locked
uv run python manage.py migrate
uv run python manage.py runserver
```

Откройте http://127.0.0.1:8000/. Миграция `0003` один раз добавляет четыре
примерных товара. Данные о цене и характеристиках демонстрационные.
Для управления каталогом создайте администратора:

```shell
uv run python manage.py createsuperuser
```

В `/admin/` можно менять описание, цену и остаток. Остаток ранее существовавших
товаров после миграции равен нулю: его необходимо указать по фактическому наличию.
Файл `products.yaml` — только пример для отдельной учебной базы; автоматический
deploy не загружает фикстуры повторно и не восстанавливает проданные остатки.

## Устройство приложения

- `shop/models.py`: товары, покупки, атомарное оформление заказа.
- `shop/forms.py`: `PurchaseForm`, обязательные поля и проверка доступности.
- `shop/views.py`: каталог и оформление через функции представлений.
- `shop/templates/shop/`: общий шаблон и страницы с классами Bootstrap 5.
- `shop/migrations/`: схема БД и первоначальные данные.
- `shop/tests/`: тесты моделей, форм, страниц, данных и конкурентных покупок.

Покупка блокирует строку товара через `select_for_update` в транзакции,
повторно проверяет остаток, сохраняет заказ и уменьшает количество на единицу.
Ошибка отменяет всю транзакцию. Товар из URL определяет заказ; клиент не может
подменить его скрытым полем. После покупки выполняется перенаправление в каталог,
поэтому обновление страницы не повторяет отправленный POST.

Стиль форм и представлений ориентирован на
[Web-sleep-app](https://github.com/NeMoVetr/Web-sleep-app): отдельные `ModelForm`,
валидация и функции представлений. Собственный CSS удалён; Bootstrap подключён
через CDN в `base.html` и действует на обеих страницах.

## Тестирование

```shell
uv run coverage run manage.py test --noinput
uv run coverage report
uv run coverage html
uv run python manage.py makemigrations --check --dry-run
```

Для тестов PostgreSQL-пользователь должен иметь право создания тестовой БД.
Тестовая база создаётся отдельно от основной и удаляется после запуска.
Минимальное покрытие CI — 95%, учитываются строки и ветвления приложения `shop`;
файлы тестов и миграций исключены из процента. Конкурентный тест использует
два отдельных подключения PostgreSQL и проверяет покупку последней единицы.

## CI/CD

GitHub Actions запускается при push в `master`, `feature/**` и при pull request:
поднимает PostgreSQL 18, устанавливает зависимости из `uv.lock`, проверяет
миграции, запускает все тесты, измеряет покрытие, сохраняет `coverage.xml`
и собирает Docker-образ. Затем запускает контейнер и проверяет HTTP-ответ
каталога. Ошибка любой проверки делает сборку неуспешной.

Для публикации на Render подготовлен `render.yaml`:

1. В своём аккаунте Render создайте Blueprint из репозитория `NeMoVetr/PTLab2`
   и ветки `master`, ознакомьтесь с условиями выбранного тарифа.
2. Blueprint создаёт веб-сервис и PostgreSQL, генерирует `SECRET_KEY` и связывает
   параметры БД. Пароли не требуется записывать в GitHub.
3. `autoDeployTrigger: checksPass` включает автоматическое развёртывание после
   успешных проверок ветки `master`. Docker запускает миграции, собирает статику
   и запускает Gunicorn. Страницу `/` Render использует для проверки доступности.
4. Адрес приложения выдаётся Render после создания сервиса. Наличие YAML-файла
   само по себе не создаёт ресурсы в аккаунте.

Спецификация: [Render Blueprint](https://render.com/docs/blueprint-spec).
Выбран бесплатный учебный тариф; ограничения и срок жизни бесплатной БД
следует проверить в аккаунте Render перед созданием. Локальная база и `.env`
не копируются в контейнер. Старый Travis/Heroku pipeline заменён GitHub Actions.

## Результаты и выводы

Разработка ведётся в `feature/luxury-shop`, созданной от `master`, с отдельными
коммитами функциональности и CI/CD. Объединение с `master` выполняется после
успешного запуска тестов.

Локально на PostgreSQL успешно выполнен 31 тест. Покрытие строк и ветвлений
приложения `shop` составляет 100% (91 исполняемая строка, 6 ветвлений).

Проверки подтверждают, что покупка уменьшает остаток, отсутствующий товар
нельзя заказать, неверная форма не меняет БД, ошибка сохранения отменяет заказ,
а два клиента не могут купить последнюю единицу одновременно. Проверяются также
CSRF, экранирование пользовательского имени, неизвестные товары, подмена
идентификатора и сохранение введённых данных при ошибке.

Основной вывод: отключённой кнопки недостаточно для контроля остатков;
правило должно проверяться в транзакции на сервере. Отдельная форма упрощает
валидацию и тестирование, миграция данных делает развёртывание воспроизводимым,
а CI выявляет ошибки до публикации. Процент покрытия относится к Python-коду,
не доказывает правильность всего приложения и не заменяет визуальную проверку.
Фактический результат публикации нужно подтвердить по адресу созданного сервиса.
